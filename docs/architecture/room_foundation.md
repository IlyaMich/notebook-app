# LIB-03 Checkpoint 2B — Room foundation (2026-10-28)

Status: **implementation candidate, pending local Gradle, instrumentation test and peer review**.
Issue: LIB-03 #18. Depends on the peer-approved `lib_03_android_repository_contract_v0_1.md` (2A).

## Physical schema and ownership

- `com.notebook.app.data.local.AppDatabase`, version **1**, single canonical Room type and production singleton in `AppDatabaseProvider` (`library.sqlite`).
- LIB-03 owns `FolderEntity`, `NotebookEntity`, `NoteEntity`, and their DAO definitions.
- UTC epoch-millisecond timestamps and content `revision: Long` match 2A. Column names follow the merged LIB-01 SQLite proposal.
- Foreign keys are `RESTRICT` (never cascading deletes). Historical original-location snapshots intentionally have no FKs.
- Folder and notebook siblings are sorted independently; ties sort by ID. Quick Notes role is unique because `system_role` has a unique index and the on-create triggers restrict non-NULL roles to `quick_notes`.
- The on-create triggers reject Quick Notes deletion/demotion/movement/trashing and direct folder self-parenting. Nontrivial ancestry, active ownership, full Trash transitions and other constraints must be enforced by repository transactions later. These trigger definitions **must be retained in every future migration**.
- Unlike the LIB-01 draft SQL, Room's autogenerated V1 CREATE TABLE statements do not enforce all draft CHECK constraints. Repository implementations must guard name, ID, ordering, deleted-batch consistency, active-owner and cycle rules. Do not claim full parity with the proposed DDL yet.

## Critical content boundary

**No note creation or duplication repository is implemented in 2B.** Room's `notes` DAO is an internal primitive only; it must never be called by UI to create a zero-page active note. `NoteLifecycleRepository` requires STO-02's `NoteContentTransactionPort` to insert an initial page or clone content in **one outer** `AppDatabase.withTransaction` call. No dummy page, second database or metadata-only fallback is permitted.

The `pages`, `elements`, assets and asset-reference tables do **not** exist in Room V1. When STO-02 extends this database, add its entity/DAO types and an **explicit migration from 1 to 2**. Do not use destructive migration. The portable `.notebook` `schemaVersion` is separate. Changes to physical V1 after any real user data is stored also require a versioned migration; do not silently replace V1 schema exports.

## Bootstrap and tests

- `AppDatabaseProvider.get(context)` is the production singleton; do not build other production instances.
- `AppDatabaseProvider.openIsolated(context,name)` is for instrumentation tests only; each test uses a distinct on-disk database.
- `NotebookRepository.ensureQuickNotes()` will provision exactly one `quick_notes` notebook in a later checkpoint, in a shared transaction. **This checkpoint guarantees at most one, not at least one**.
- Run `:app:assembleDebug`, `:app:testDebugUnitTest`, `:app:connectedDebugAndroidTest --tests` availability varies; preferred `:app:connectedDebugAndroidTest` on a booted emulator. Tests cover reopen, FKs, Quick Notes protection and self-parenting.
- Room compiler exports schema JSON to `android/app/schemas/.../1.json`. Review and commit the generated schema JSON with the PR. It is not pre-generated in this package because no Android toolchain was run here.
